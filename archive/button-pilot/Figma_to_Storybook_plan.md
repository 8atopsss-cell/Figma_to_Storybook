# План переноса компонентов из Figma в Storybook

Дата: 1 октября 2026 года.
Выбранный подход: перенос через Figma MCP с общими токенами, правилами реализации и проверкой компонентов.

> Уточнение пользователя от 1 октября 2026: текущая итерация — только кнопки. Input и Card, упомянутые ниже, отложены и не являются условиями завершения этой итерации. Стек: новый React + TypeScript + CSS Modules; Vite предложен как сборщик. Принимает результат пользователь. Актуальный источник: `SD Enterprice`, страница `UI kit`. Текущий реестр: `docs/component-registry.md`, проект контракта кнопок: `docs/component-contracts.md`.

## 1. Цель и границы

Создать библиотеку переиспользуемых компонентов в коде и каталог Storybook, в котором можно проверить их внешний вид, настройки, состояния и поведение.

Результат должен быть пригоден для использования разработчиками в продукте. Визуального сходства с Figma недостаточно: нужны понятные свойства, корректная работа с клавиатурой, устойчивость к разному содержимому и предсказуемое обновление.

В первую итерацию входят:

- настройка проекта и Storybook;
- перенос базовых токенов;
- правила для Codex;
- пилот: кнопки; сначала Button с текстом, затем IconButton;
- stories, документация и необходимые проверки;
- регламент дальнейшего переноса и обновлений.

Code Connect, автоматическая двусторонняя синхронизация и массовый перенос всей библиотеки в первую итерацию не входят. Изменения дизайна переносим отдельными задачами, с проверкой результата.

## 2. Что известно и что нужно выяснить

По словам пользователя, Codex уже подключён к Figma через MCP. Конкретный файл, доступность инструментов, состав библиотеки и репозиторий пока не проверены. Новый репозиторий в рамках текущей беседы ещё не создан.

| Вопрос | Предлагаемое решение | Когда определить |
|---|---|---|
| Есть ли действующий продукт и его код? | Если есть — использовать его стек и соглашения | До настройки проекта |
| Если проекта нет, какой стек использовать? | React + TypeScript + Vite, Storybook для React/Vite | На старте пилота |
| Где хранить код? | Репозиторий GitHub; предложенное имя `figma-to-storybook` | До первого коммита |
| Какая система стилей? | При новом проекте — CSS Modules и CSS variables; в существующем — принятый подход | До первого компонента |
| Какие темы нужны? | Только темы, действительно предусмотренные дизайном | До переноса токенов |
| Какие шрифты и иконки используются? | Исходные ресурсы; проверить возможность использования в вебе | До визуальной приёмки |
| Кто принимает результат? | Дизайнер — внешний вид; разработчик — API и интеграцию, если он участвует | До завершения пилота |
| Как библиотека попадёт в продукт? | Для пилота достаточно исходников; способ поставки согласовать до масштабирования | После пилота |

Эти пункты — рабочие предложения, а не уже согласованные решения. Номера версий зависимостей выбираем при настройке по совместимости, затем фиксируем lock-файлом.

## 3. Распределение ответственности

| Участник | Ответственность |
|---|---|
| Дизайнер | Исходные компоненты, состояния, правила поведения, визуальная приёмка |
| Codex | Анализ Figma и кода, реализация, stories, проверки, документация изменений |
| Разработчик, если участвует | Совместимость с продуктом, публичный API, архитектура, ревью |

Если разработчик пока не участвует, отдельно фиксируем, что библиотека прошла дизайнерскую приёмку, а интеграция в продукт ещё не подтверждена.

## 4. Этап 1 — проверить доступ и составить инвентаризацию

### Действия

- [ ] Получить ссылку на файл Figma и ссылки на точные узлы пилотных компонентов.
- [ ] Проверить получение структуры и скриншота одного компонента через MCP.
- [ ] Уточнить тип MCP: официальный Figma или другой сервер. Не предполагать одинаковые инструменты.
- [ ] Проверить доступ к переменным, вариантам и ресурсам; зафиксировать ограничения.
- [ ] Найти основной компонент или component set, а не случайный экземпляр на экране.
- [ ] Выявить уже существующие реализации в коде, если репозиторий не пустой.
- [ ] Составить реестр компонентов и выбрать порядок переноса.

Для официального Figma MCP используем доступные `get_design_context`, `get_screenshot`, `get_metadata` и инструменты работы с переменными. Если сервер другой, применяем его эквиваленты. Если контекст обрезан, получаем карту узлов и читаем нужные части отдельно.

Реестр должен содержать:

| Поле | Что записываем |
|---|---|
| Название | Button, Input, Card и другие |
| Figma | Ссылка на основной компонент, node ID |
| Варианты | Размеры, оформление, темы |
| Состояния | Обычное, hover, focus, disabled, error и другие применимые |
| Содержимое | Текст, иконки, вложенные элементы |
| Зависимости | Токены и другие компоненты |
| Реализация | Путь в коде и story ID, когда появятся |
| Статус | Не начат / нужен ответ / реализован / проверен / принят |
| Проверенный источник | Дата чтения Figma и доступный идентификатор версии, если он есть |

**Критерий завершения:** доступ проверен, пилот выбран, неизвестные состояния и зависимости перечислены. Весь UI-kit одним запросом не переносим.

## 5. Этап 2 — подготовить Figma для пилота

- [ ] Пилотные элементы оформлены как компоненты с понятными названиями.
- [ ] Варианты и свойства названы последовательно.
- [ ] Auto Layout отражает реальное поведение размеров и отступов.
- [ ] Цвета и другие повторяющиеся значения связаны с переменными или стилями, где это возможно.
- [ ] Определены необходимые состояния и поведение, в том числе не показанные на макете.
- [ ] Уточнено, что происходит с длинным текстом, пустым значением и изменением ширины.
- [ ] Подготовлены шрифты, иконки и изображения.

Не нужно переименовывать всю библиотеку ради старта. Исправляем пилот и обнаруженные проблемы; общие правила затем распространяем на остальные компоненты.

**Критерий завершения:** для каждого пилотного компонента можно объяснить его варианты, размеры, содержимое и взаимодействия. Отсутствующее поведение оформлено как открытый вопрос, а не придумано незаметно.

## 6. Этап 3 — настроить проект

При существующем проекте сначала изучаем его структуру. При новом используем предложенную ниже структуру, адаптируя её после выбора стека.

| Путь | Назначение |
|---|---|
| `src/components/` | Компоненты, их стили и stories рядом с исходниками |
| `src/tokens/` | Канонические значения токенов и их связи |
| `src/styles/` | Сгенерированные CSS variables, глобальные стили и шрифты |
| `src/assets/` | Реальные иконки и другие ресурсы |
| `src/index.ts` | Публичные экспорты библиотеки |
| `.storybook/` | Настройки каталога, общие декораторы, темы |
| `docs/component-registry.md` | Реестр и ссылки между Figma и кодом |
| `docs/component-contracts.md` | Согласованные свойства и поведение |
| `docs/design-system-rules.md` | Правила реализации |
| `docs/token-mapping.md` | Соответствие Figma и токенов кода |
| `AGENTS.md` | Краткие обязательные инструкции для Codex со ссылками на документы |
| `CHANGELOG.md` | Значимые изменения библиотеки |

### Действия

- [ ] Настроить TypeScript, Storybook, стили и загрузку шрифтов.
- [ ] Добавить одну техническую story и проверить запуск и сборку.
- [ ] Настроить проверку типов и линтер.
- [ ] Подключить документацию и Controls для настройки свойств в Storybook.
- [ ] Подключить Designs addon для просмотра Figma рядом с реализацией, если доступ к embed позволяет.
- [ ] Подключить необходимые инструменты проверки взаимодействий и доступности.
- [ ] Описать запуск и проверки в README.
- [ ] Зафиксировать зависимости и команды проекта.

Предлагаемые имена команд: `storybook`, `build-storybook`, `typecheck`, `lint`, `test`. Реальное содержимое команд настраиваем под выбранные версии; наличие имени само по себе не означает, что проверка работает.

**Критерий завершения:** другой участник может установить зависимости, запустить Storybook и собрать его по README.

## 7. Этап 4 — перенести токены

Токен — именованное значение, которое компоненты используют совместно: например, цвет текста или радиус поля.

### Порядок

1. Прочитать переменные и стили, нужные пилоту, вместе с их алиасами и режимами.
2. Составить таблицу соответствия Figma → код.
3. Разделить базовые значения и смысловые назначения, если такая модель подходит исходному дизайну.
4. Хранить канонические значения в одном месте, например JSON. Генерировать из него CSS variables небольшим скриптом; вручную сгенерированный CSS не редактировать.
5. Добавить демонстрацию цветов, типографики и других токенов в Storybook.
6. Проверить, что пилотные компоненты используют общие токены.

Пример, а не реальные значения из файла:

| Figma | Токен кода | Использование |
|---|---|---|
| `Color/Text/Primary` | `--color-text-primary` | Основной текст |
| `Color/Action/Primary` | `--color-action-primary` | Основное действие |
| `Radius/Control` | `--radius-control` | Кнопка и поле, если дизайн задаёт общий радиус |
| `Space/Control/Inline` | `--space-control-inline` | Горизонтальный внутренний отступ |

### Правила

- Сохранять смысловые алиасы, а не только итоговые HEX и числа.
- Не объявлять каждое случайное значение новым общим токеном.
- Различать внутренние отступы компонента и его положение в родительском контейнере.
- Не добавлять тёмную тему, если она не определена в исходной системе.
- Если выгрузка неполная, явно документировать ручное соответствие и способ проверки.
- Не считать наличие MCP готовой автоматической синхронизацией токенов.

**Критерий завершения:** значения пилота имеют понятное происхождение; изменение общего токена отражается во всех компонентах, которые его используют.

## 8. Этап 5 — зафиксировать свойства и правила компонентов

До реализации согласуем краткий контракт каждого компонента: назначение, свойства, значения по умолчанию, состояния, поведение, допустимое содержимое и ограничения.

| Компонент | Предлагаемые свойства | Что нужно уточнить |
|---|---|---|
| Button | `variant`, `size`, `disabled`, `children`; иконки и loading при наличии | Поведение loading, кнопка или ссылка, ширина по содержимому или контейнеру |
| Input | `label`, `value/defaultValue`, `onChange`, `disabled`, `readOnly`, ошибка и подсказка | Вид поля, обязательность, отображение ошибки, порядок подсказок |
| Card | Содержимое или согласованные слоты; вариант оформления при наличии | Статичная или интерактивная карточка, структура вложений |

Это стартовая модель. Она не должна заставлять исходный дизайн принимать лишние настройки.

### Правила для Codex

- Сначала читать контракт, токены и уже созданные компоненты.
- Использовать семантический HTML и реальные ресурсы.
- Не создавать отдельный компонент для каждого варианта одной кнопки.
- Не превращать настоящие hover и focus в публичные свойства ради имитации состояния.
- Не использовать абсолютное позиционирование для обычной компоновки без необходимости.
- Не добавлять зависимости и альтернативную систему стилей без обоснования.
- Повторно использовать существующие элементы; не собирать копии их разметки.
- Не менять публичные свойства другого компонента незаметно.
- Не считать скриншот полным описанием поведения.

**Критерий завершения:** контракт позволяет реализовать и проверить компонент без догадок о существенном поведении.

## 9. Этап 6 — перенести пилот

Текущий порядок: Button → IconButton. Input и Card отложены. Каждый следующий компонент использует уже утверждённые правила и общие элементы.

### Цикл для одного компонента

1. Прочитать точные узлы Figma, варианты, переменные и ресурсы.
2. Получить скриншоты нужных вариантов. Проверить полноту контекста.
3. Сопоставить данные с контрактом; записать расхождения и открытые вопросы.
4. Реализовать компонент и стили в рамках проекта.
5. Добавить stories для основных вариантов, состояний и пограничного содержимого.
6. Проверить типы, сборку и необходимые взаимодействия.
7. Открыть Storybook в браузере и сравнить с Figma при одинаковом размере и содержимом.
8. Исправить расхождения, получить визуальную приёмку.
9. Обновить реестр и описание изменений; зафиксировать отдельным коммитом или PR.

### Минимальная матрица приёмки

| Компонент | Внешний вид | Поведение и пограничные случаи |
|---|---|---|
| Button | Основные размеры и оформления, иконки, disabled, hover, focus | Клик, Enter/Space для кнопки, disabled не вызывает действие, длинный текст |
| Input | Пустое и заполненное поле, подсказка, ошибка, disabled, focus | Ввод, связь label с полем, сообщение об ошибке, controlled/uncontrolled при поддержке, readOnly |
| Card | Согласованное содержимое и варианты | Узкий контейнер, длинный заголовок, отсутствие необязательных блоков; клавиатура только для интерактивного варианта |

Нужные hover/focus-состояния получаем реальным взаимодействием в браузере или тестом. Для визуального снимка состояние должно быть воспроизводимо.

Не генерируем все комбинации свойств автоматически: выбираем отдельные примеры для каждого варианта и рискованных сочетаний. Stories служат понятными примерами использования, а не бесконечной таблицей комбинаций.

**Критерий завершения текущего пилота:** согласованные кнопки приняты, в них нет дублирующей системы токенов, API согласован, проверки воспроизводимы, известные ограничения записаны. Импорт вне Storybook и композиция кнопок проверены до завершения пилота.

## 10. Как проверять результат

| Проверка | Что подтверждает | Когда |
|---|---|---|
| Типы и линтер | Корректность кода в рамках правил проекта | После изменения |
| Сборка Storybook | Каталог собирается | Перед приёмкой |
| Сравнение с Figma | Соответствие исходному дизайну | При первом переносе и изменении дизайна |
| Тест взаимодействия | Существенное поведение: ввод, клики, клавиатура | Для интерактивных компонентов |
| Автоматическая проверка доступности | Часть распространённых ошибок | Для принятых stories |
| Ручная проверка клавиатуры | Видимый focus, порядок переходов, управление | При приёмке интерактивного компонента |
| Визуальная регрессия | Отличия от утверждённой реализации | После утверждения исходного результата |

Автоматическая проверка доступности не заменяет ручную. Визуальная регрессия не доказывает соответствие Figma: она сравнивает реализацию с ранее утверждённым снимком.

После пилота можно добавить снимки через Playwright для выбранных stories. Нужно зафиксировать браузер, viewport, шрифты и данные, отключить нестабильные анимации и согласовать допустимые расхождения. Эталоны обновляем после просмотра изменений, а не автоматически вслед за любым новым кодом.

Chromatic — возможное дальнейшее расширение. В первом пилоте он не обязателен.

## 11. Этап 7 — масштабировать библиотеку

После пилота пересматриваем правила на основании выявленных проблем.

- [ ] Проверить, что компоненты можно импортировать вне Storybook.
- [ ] Собрать небольшой пример интерфейса из пилотных компонентов, чтобы выявить проблемы композиции.
- [ ] Согласовать способ поставки в продукт: исходники в общем репозитории или отдельный пакет.
- [ ] Выбирать следующий набор по зависимостям и приоритету продукта.
- [ ] Переносить небольшие группы с отдельной приёмкой.
- [ ] Сохранять обратную связь и ограничения в реестре.

Предлагаемый порядок после пилота: типографика и иконки → Badge и Checkbox → Select и Tooltip → Dialog и меню → составные блоки. Реальный порядок зависит от исходного UI-kit. Сложные интерактивные элементы требуют отдельных контрактов; внешний вид не описывает управление фокусом и клавиатурой.

## 12. Как обновлять компоненты после изменения Figma

1. Дизайнер указывает изменённые компоненты, ссылки и смысл изменения.
2. Codex заново читает нужные узлы; не использует старый контекст как текущую спецификацию.
3. Определяет, что изменилось: токен, стиль, содержимое, состояние или публичное свойство.
4. Проверяет затронутые компоненты и stories. Изменение общего токена требует проверки всех его потребителей.
5. Вносит ограниченное изменение в существующую реализацию.
6. Запускает проверки, показывает визуальные отличия и перечисляет влияние на использование.
7. После приёмки обновляет эталоны, реестр, документацию и CHANGELOG.

Изменение цвета обычно не меняет API. Переименование свойства или удаление варианта может сломать использование: такие изменения отмечаем отдельно и приводим пример миграции.

Для регулярной работы можно включить в GitHub автоматическую проверку типов, сборки и тестов при PR. Это автоматизация проверок кода, а не автоматическое обнаружение и перенос всех изменений Figma.

## 13. Шаблон задачи для Codex

```text
Перенеси компонент [название] из Figma: [ссылка на точный узел].

Перед реализацией прочитай AGENTS.md, правила дизайн-системы,
контракт компонента, токены и существующие реализации.

Через подключённый Figma MCP получи структуру компонента,
нужные варианты, переменные, ресурсы и скриншоты.
Если данные обрезаны, получи структуру узлов и прочитай нужные части отдельно.

Используй стек и стили проекта. Сохрани соответствие общим токенам.
Собери переиспользуемый компонент с согласованными свойствами.
Если существенное поведение не описано, перечисли вопрос до его реализации.

Добавь stories для согласованных вариантов, состояний и пограничных случаев.
Проверь существенные взаимодействия и доступность.
Запусти проверки проекта и сравни компонент в браузере со скриншотами Figma.

Обнови реестр. В отчёте укажи изменения, выполненные проверки,
расхождения с Figma и ограничения. Не утверждай успешную проверку,
если соответствующая проверка не выполнялась.
```

## 14. Очередь работы и точки принятия решений

| Шаг | Результат | Следующее действие |
|---|---|---|
| 1. Вводные и доступ | Ссылки, стек, список пилота, рабочий MCP | Подготовка Figma |
| 2. Подготовка пилота | Понятные варианты и поведение | Настройка проекта |
| 3. Проект | Запускаемый Storybook и проверки | Токены |
| 4. Токены и контракты | Общая основа и правила | Реализация Button |
| 5. Button | Первый принятый компонент | Скорректировать правила и перенести IconButton |
| 6. IconButton | Проверенный пилот кнопок | Проверка композиции и поставки |
| 7. Масштабирование | Очередь следующих компонентов | Перенос небольшими группами |

Календарные сроки определяем после просмотра файла. Пока неизвестны количество вариантов, качество исходной структуры, наличие кода и полнота описания поведения; точная оценка времени сейчас была бы выдуманной.

## 15. Критерии успеха первой итерации

- [ ] Storybook запускается и собирается по README.
- [ ] Button и согласованные IconButton доступны для использования вне Storybook.
- [ ] Основные параметры используют общие токены.
- [ ] Варианты и свойства связаны с исходными компонентами Figma.
- [ ] Существенные состояния показаны и проверены.
- [ ] Длинное содержимое и изменение ширины не приводят к необъяснённым поломкам.
- [ ] Интерактивные компоненты проверены с клавиатурой.
- [ ] Визуальные расхождения исправлены или явно приняты.
- [ ] Нет неподтверждённого статуса «готово»: в реестре указаны выполненные проверки.
- [ ] Следующий компонент можно перенести по тем же правилам, не меняя основу проекта.
